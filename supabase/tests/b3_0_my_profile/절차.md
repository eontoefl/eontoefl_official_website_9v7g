# 계약 3-0 — 본인 회원 정보 함수 `public.my_profile()` 시험 절차 (브레인방용)

**이 폴더의 SQL·도구와 마이그레이션·되돌리기 SQL은 한 번도 실행되지 않았다.** 작업방은 파일만 썼다. SQL은 실행도 문법 확인도 하지 못했고, `profile_matrix.mjs`는 가짜 응답(네트워크 없음)으로만 돌려 봤다. 가짜 응답은 실제 동작을 대신하지 않는다.

대상은 **시험 프로젝트 `hmncdheiwqwekdbtijar`뿐**이다. 운영(`qpqjevecjejvbeuogtbx`)에는 아무것도 보내지 않는다.

- SQL 통로는 한 요청의 여러 문장을 같은 접속으로 보내고 마지막 문장의 결과를 돌려준다(2-나-1에서 확인됨). 결과가 jsonb 한 칸인 SQL은 그 결과를 파일로 저장해 도구에 넘긴다(`[{"result":{…}}]` 모양 그대로 받는다).
- `fixtures_up.sql`·`fixtures_down.sql`은 같은 요청의 맨 앞에 `set b3_0.test_project_ref = 'hmncdheiwqwekdbtijar';`가 있어야 돈다. **그 값은 실제 연결 대상을 증명하지 못한다** — 실행 직전에 SQL 통로가 가리키는 프로젝트의 ref를 직접 확인한다.

## 함수가 하는 일 (마이그레이션이 만드는 것)

`POST /rest/v1/rpc/my_profile`(본문 `{}`), `authenticated`만 실행. 인자 없음.

| 호출자 | 돌려주는 값 |
|---|---|
| 살아 있는 일반 로그인 + 회원 대응이 있는 정상 회원 | `200` `{"state":"ok","profile":{"id","name","nickname","email","phone","timezone"}}` — 이 여섯 열만 |
| 차단된 회원(탈퇴 처리 중과 겹쳐도) | `200` `{"state":"blocked"}` |
| 탈퇴 처리 중 회원 | `200` `{"state":"withdrawal_pending"}` |
| 회원 대응이 없거나, 로그인 기록이 끝났거나 만료 | `200` `{"state":"no_member"}` |
| 점검 중이고 예외가 아님 | `503` (`code` `PT503`, `message` `maintenance`) — 회원 행을 읽기 전에 끝낸다 |
| `GET`·`HEAD` | `405` — 함수는 `VOLATILE`이고, 함수 안에서도 요청 메서드가 `POST`가 아니면 `PT405`로 끝낸다 |
| 비로그인(공개 키)·서비스 열쇠 | `401`·`403` (`code` `42501` — 실행 권한 없음) |

`200`으로 돌려주는 네 상태에는 전부 `Cache-Control: private, no-store`가 붙는다. 함수는 아무것도 고치지 않는다.

- **함정 행**: 회원번호(`id`)가 계정 `zzb3p0_n`의 **로그인 계정 번호와 같은** 회원 행 하나(대응표에는 없다). 함수가 로그인 계정 번호를 회원번호로 쓰면 `n`에게 이 행이 나간다 — `n`의 기대값은 `no_member`이고 함정 행의 값은 어느 응답에도 나오면 안 된다.

- 자격은 60분짜리다. 도구는 남은 시간이 2분 아래인 자격으로는 요청을 보내지 않는다. 모자라면 같은 순서로 다시 받는다.
- 도구는 요청 전에 확인한다: 주소가 정확히 시험 프로젝트, 열쇠·자격의 ref·발급자·역할, 자격의 계정이 `expect.json`의 그 계정과 같음, G1·GM1은 aal1이고 G2·GM2는 aal2, 서로 다른 로그인 기록. 어긋나면 **요청 0으로 멈춘다**(종료 값 2).

## 도구의 단계와 판정

| `--phase` | 무엇 | 요청 |
|---|---|---|
| `plan --state <상태>` | 그 상태의 칸과 기대값을 적는다 | 0 |
| `sessions-sql` | 지금 자격들의 로그인 기록을 읽는 SQL을 적는다 | 0 |
| `absent` | 적용 전 기준: 그 RPC가 "등록되지 않은 함수"로 응답하는가(지문에 함수 없음과 **둘 다**) | 3 |
| `matrix --state <상태>` | 대조표: 자격 12 × `POST`·`GET`·`HEAD` + 인자를 붙인 요청 4 | 40 |
| `revoked --kind … --step …` | JWT 만료 / 로그인 기록 만료 / 로그아웃 | 2 |
| `rows-compare --before --after` | `rows_md5.sql` 결과 둘을 견준다 | 0 |
| `compare --a --b [--ignore 키,…]` | 지문 결과 둘을 견준다(`read_at`은 늘 뺀다) | 0 |
| `body-md5` | 마이그레이션 파일의 함수 본문 md5 | 0 |

`--state`는 "지금 시험 프로젝트가 어떤 상태인가"다. **도구는 상태를 스스로 알지 못한다 — 재기 직전에 `fingerprint.sql`을 떠서 `--fingerprint`로 넘긴다.** 도구는 그 파일로 함수의 존재·실행 권한·점검 상태·공통 확인 설정·예외 명단이 `--state`와 맞는지 보고, 맞지 않으면 요청을 보내지 않는다(종료 값 3 "기준선 불일치"). 30분보다 오래된 지문·로그인 기록 파일은 받지 않는다.

| `--state` | 점검(`site_state.phase`) | 공통 확인 설정(`pgrst.db_pre_request`) |
|---|---|---|
| `normal` | `normal` | 없음 |
| `normal-hook` | `normal` | 걸림 |
| `maint-hook` | `maintenance` (예외 명단에 A만) | 걸림 |
| `maint` | `maintenance` (예외 명단에 A만) | 없음 |

판정(칸마다): **통과** = 기대값과 전부 같음 / **기대와 다름** = 응답은 왔는데 하나라도 다름 / **미확인** = 네트워크 오류·시간 초과·429·기대하지 않은 5xx(성공으로도 실패로도 세지 않는다).
- `ok` 칸: `200`, 응답의 키가 **정확히** `state`·`profile`, `profile`의 키가 **정확히 여섯 개**, 값이 `expect.json`의 그 회원 값과 같음(없는 값은 `null`), `Cache-Control`이 `private, no-store`.
- `blocked`·`withdrawal_pending`·`no_member` 칸: `200`, 응답의 키가 **정확히 `state` 하나**, `Cache-Control`이 `private, no-store`.
- 모든 칸: 응답에 금지 키(`password`·`role`·`level`·`blocked`·`withdrawal_*`·`auth_user_id`·`member_id` 등)가 없고, 본문 글자 전체에 `password`라는 글자와 **금지 값**이 없다. 금지 값 = 합성 회원 전원(함정 행 포함)의 회원번호·이름·별명·이메일·전화, 옛 비밀번호 열의 합성 표식, 탈퇴 사유 표식, 로그인 계정 번호. `ok` 칸에서는 그 회원 본인의 여섯 값만 허용한다 — 그래서 A의 응답에 B의 값이 있으면(그 반대도) 잡힌다.
- 인자를 붙인 요청(A가 B의 회원번호·이메일을, B가 A의 회원번호를 본문에 넣음): `404`이고 `code`가 `PGRST202`(함수를 찾지 못함), 그 회원의 정보 없음.
- `GET`·`HEAD`: **상태 코드로** 판정한다(`HEAD`는 본문이 비어 있다는 것으로 판정하지 않는다). 로그인 자격은 `405`, 공개 키·서비스 열쇠는 `401`·`403`·`405` 중 하나. 결과의 `rejected_by`에 누가 거절했는지 적힌다(`code`가 `PT405`면 함수 안의 확인, 그 밖이면 PostgREST).
- 점검 중(`maint`·`maint-hook`): 예외 회원 A와 6자리 후 관리자(G는 `no_member`, GM은 본인 `ok`)만 통과, 나머지는 `503`·`PT503`·`maintenance`. `maint-hook`에서는 공개 키·서비스 열쇠도 `503`이다(공통 확인이 먼저다).

종료 값: 0 = 전부 통과 / 1 = 기대와 다름 또는 미확인이 있음 / 2 = 요청 전에 멈춤 / 3 = 기준선 불일치.
지문을 견줄 때(`compare`): 그사이 로그인을 새로 했으면 `counts.sessions`만 다를 수 있다. 그 키만 다르면 `--ignore sessions`를 붙여 다시 견주고 그렇게 했다고 기록한다(다른 키가 다르면 통과가 아니다).
결과 파일에서 보는 곳: `summary`(통과·기대와 다름·미확인·금지 키·값, 자격별), `mismatches`, `undetermined`, `cells`(칸마다 상태 코드·`code`·응답의 키·`Cache-Control`·문제), `fingerprint_check`, `session_check`. 결과에는 응답 본문과 열쇠·자격이 적히지 않는다.

## 중단 규칙

- 대상이 `hmncdheiwqwekdbtijar`가 아니거나 확인할 수 없으면 아무것도 쓰지 않고 멈춘다.
- 어느 단계든 기대와 다르면 다음 단계로 넘어가지 않는다. 무엇이 왔는지 기록한다.
- **점검 상태나 공통 확인 설정을 켠 채로 멈추지 않는다**: 멈출 때는 먼저 7-6(원복)을 한다. 그다음 실패나 미확인이 남았으면 9단계(되돌리기)로 가서 함수를 남기지 않고, 11단계로 합성 자료를 정리한다.
- 공통 확인 설정은 **시작할 때 없을 때만** 건다(7-2의 조건). 이미 있으면 건드리지 않고 멈춘다.

## 이 절차가 확인하지 않는 것

- **브라우저가 쓰는 실제 배포 경로(중간 저장소 포함)에서의 `Cache-Control`.** 도구는 API 주소에 직접 보낸 요청의 머리글만 본다.
- **`GET`·`HEAD`를 누가 거절하는가는 PostgREST 판에 달려 있다.** 작업방은 확인하지 못했다. 이 함수는 쓰기가 없어서 `VOLATILE`만으로는 막히지 않을 수 있다고 보고 함수 안에 메서드 확인을 넣었다 — 결과의 `rejected_by`가 실제로 어느 쪽이었는지 보여 준다.
- **접근 등록부(`access_grant`)에 대상으로 적힌 회원의 정상 로그인.** 함수는 그 표를 읽지 않으므로 거절하지 않게 돼 있지만, 그런 행을 넣고 재지는 않는다.
- **회원 표가 잠긴 뒤(묶음 5)의 동작.** 지금 회원 표에는 행 보안이 없다. 소유자 권한으로 읽으므로 행 보안을 켜도 돌게 돼 있으나, `FORCE ROW LEVEL SECURITY`를 걸면 소유자도 정책을 따른다 — 그때 다시 잰다.
- **책 연결·대리 자격.** 이 RPC의 입력이 아니다(서버 중계로만 쓰인다). 그런 자격으로 이 RPC를 부르는 경우는 재지 않는다.
- **동시에 여러 요청이 오는 경우, 응답 시간.**
- 예외 명단의 만료(`expires_at`)·다른 점검 번호의 예외 — 2-가의 시험이 본 것이고 여기서는 다시 재지 않는다.
- 로그인 기록이 살아 있다는 것은 넘겨받은 파일을 믿는다. 파일을 읽은 뒤 재는 동안 기록이 끝나는 경우는 잡지 못한다(그 칸은 "기대와 다름"으로 나온다).
