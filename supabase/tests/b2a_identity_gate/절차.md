### 4-6. `resolve_grant` — 기준 3

장부 행 넣기(SQL, postgres). 지문은 시험용 글자의 sha-256 16진수다(자격 원문이 아니다).
```sql
insert into security_private.access_grant
  (credential_digest, purpose, actor_auth_user_id, target_member_id, issued_at, expires_at, revoked_at)
values

  (pg_catalog.encode(pg_catalog.sha256('zz-b2a-d1'::bytea), 'hex'), 'book',  null,           '<A_회원번호>', pg_catalog.now(),                         pg_catalog.now() + interval '1 hour',     null),
  -- D2 대리·정상(행위자 G, 20분)
  (pg_catalog.encode(pg_catalog.sha256('zz-b2a-d2'::bytea), 'hex'), 'proxy', '<G_계정번호>', '<A_회원번호>', pg_catalog.now(),                         pg_catalog.now() + interval '20 minutes', null),
  -- D3 만료됨
  (pg_catalog.encode(pg_catalog.sha256('zz-b2a-d3'::bytea), 'hex'), 'book',  null,           '<A_회원번호>', pg_catalog.now() - interval '2 hours',    pg_catalog.now() - interval '1 hour',     null),

insert into security_private.access_grant (credential_digest, purpose, target_member_id, issued_at, expires_at)
values (pg_catalog.encode(pg_catalog.sha256('zz-b2a-edge-exp'::bytea), 'hex'), 'book', '<A_회원번호>',
        pg_catalog.now() - interval '10 minutes', pg_catalog.now());            -- 만료 시각 = 지금
insert into security_private.access_grant (credential_digest, purpose, target_member_id, issued_at, expires_at)
values (pg_catalog.encode(pg_catalog.sha256('zz-b2a-edge-iss'::bytea), 'hex'), 'book', '<A_회원번호>',
        pg_catalog.now(), pg_catalog.now() + interval '10 minutes');            -- 발급 시각 = 지금
select pg_catalog.count(*) as expect_0 from security_private.resolve_grant(
  pg_catalog.encode(pg_catalog.sha256('zz-b2a-edge-exp'::bytea), 'hex'), 'book_read');
select pg_catalog.count(*) as expect_1 from security_private.resolve_grant(
  pg_catalog.encode(pg_catalog.sha256('zz-b2a-edge-iss'::bytea), 'hex'), 'book_read');
rollback;
```
| 보낼 요청 | 기대 응답 | 변화 |
|---|---|---|
| 위 묶음 | `expect_0` = 0, `expect_1` = 1 | 없음(rollback) |

| `purpose='proxy'`, 행위자 G, `expires_at = issued_at + interval '30 minutes 1 second'` | `23514` (`access_grant_proxy_check`) | 0 |
| `purpose='proxy'`, 행위자 G, `issued_at = T`, `expires_at = T + interval '30 minutes'`(정확히 30분) — `begin; … rollback;` 안에서 | 성공(경계는 허용) | 0 (rollback) |
| `purpose='other'` | `23514` (`access_grant_purpose_check`) | 0 |

| KE | `rpc/my_site_access` | `{"allowed": true, "is_admin": false}`, 머리글 있음 | 없음 |
| KS (서비스 열쇠) | `PATCH …/zz_b2a_member_row?member_id=eq.<A_회원번호>` `{"note":"KS-maint"}` / M / open_row GET / RG(D1, `book_read`) / `rpc/zz_b2a_probe` | 전부 `503` | 0 |
| KX | open_row GET | `401` | 0 |

예외 명단의 경계(같은 `maintenance` 상태에서 SQL로 바꿔 가며):
| SQL로 바꾸는 것 | 자격·요청 | 기대 응답 | 변화 |
|---|---|---|---|
| E의 예외 `expires_at`을 과거로 | KE로 E 행 PATCH | `503` | 0 |
| E의 예외 `expires_at`을 미래로 | 같은 요청 | `200` 1행 | 바뀜 |
| `site_state.maintenance_id`를 102로(예외는 101에만 있음) | 같은 요청 | `503` | 0 |
| `maintenance_id`를 다시 101로, `expires_at`을 null로 | 같은 요청 | `200` 1행 | 바뀜 |
| (그대로) E 전체 로그아웃 뒤 **이미 받아 둔 KE** | 같은 요청 | `503` | 0. 끝나면 E로 다시 로그인 |

**5-4. `site_state` 행이 없는 경우** (설정 행이 없으면 통과가 아니라 거절)
```sql
delete from security_private.site_state where id = 1;
```
| 자격 | 보낼 요청 | 기대 응답 | 변화 |
|---|---|---|---|
| K0, KA, KE, KG2″, KS | open_row GET(또는 각자의 쓰기) | 전부 `503` | 0 |
| K0, KA | `rpc/site_status` | `200` `{"phase": "unknown"}` | 없음 |
| KG2″ | `rpc/my_site_access` | `{"allowed": false, "is_admin": true}` | 없음 |
끝나면 행을 다시 넣는다:
```sql
insert into security_private.site_state (id, maintenance_id, phase, message) values (1, 101, 'maintenance', 'zz-b2a 시험');
```

**5-5. 점검 끝** (끝난 점검 번호를 구분할 수 있는가)
```sql
update security_private.site_state
   set phase = 'normal', last_ended_maintenance_id = 101, last_ended_at = pg_catalog.now(), updated_at = pg_catalog.now()
 where id = 1;
```
| 자격 | 보낼 요청 | 기대 응답 | 변화 |
|---|---|---|---|
| K0, KA, KS | `rpc/site_status` | 같은 본문: `phase` `normal`, `maintenance_id` 101, `last_ended_maintenance_id` 101 | 없음 |
| K0, KA, KS | 5-1의 요청 | 5-1과 같음(전부 정상) | 각자 쓰기만 |
| K0 | 기준 요청 R1~R3 | 2-3과 같음 | 없음 |

## 6단계 — 설정 원복 → 다시 적용(훅 재적용 검증) → 다시 원복 (기준 5)

**6-1. 원복** — "2-1에서 기록한 값으로 되돌리는 것"이다. 기존 값이 없었으므로(5-0의 조건):
```sql
alter role authenticator reset pgrst.db_pre_request;
notify pgrst, 'reload config';
```
| 보낼 요청 | 기대 응답 | 변화 |
|---|---|---|
| 2-1의 질의 | 2-1에서 저장한 것과 **글자 단위로 같음** | 역할 설정이 원래대로 |
| K0: 기준 요청 R1~R3 | 2-3과 같음 | 없음 |
| SQL로 `phase = 'maintenance'`로 바꾼 뒤 KA: WA / K0: open_row PATCH | `200` 1행 — 설정이 없으면 점검 값을 켜도 막히지 않는다(막는 것이 설정임을 확인) | 바뀜 |

**6-2. 다시 적용(훅 재적용)** — `phase = 'maintenance'`, `maintenance_id = 101`, E의 예외가 있는 상태에서 5-0의 두 줄을 다시 실행.
| 자격 | 보낼 요청 | 기대 응답 | 기대하는 실제 행 변화 |
|---|---|---|---|
| KA (일반 회원) | WA | `503` | 0 |
| KS (서비스 열쇠) | `PATCH …/zz_b2a_member_row?member_id=eq.<A_회원번호>` | `503` | 0 |
| K0 | open_row PATCH | `503` | 0 |
| KE (예외 회원) | E 행 PATCH | `200` 1행 | E의 행만 |
| KG2″ (대표 6자리 후) | F | `200` 1행 | `flag` |
| 전부 | `rpc/site_status` | 같은 본문 | 없음 |

**6-3. 다시 원복**
```sql
update security_private.site_state set phase = 'normal', updated_at = pg_catalog.now() where id = 1;
alter role authenticator reset pgrst.db_pre_request;
notify pgrst, 'reload config';
```
| 보낼 요청 | 기대 응답 | 변화 |
|---|---|---|
| 2-1의 질의 | 2-1과 글자 단위로 같음 | 원래대로 |
| K0: 기준 요청 R1~R3, open_row PATCH | 2-3과 같음 / `200` 1행 | 없음 / 바뀜 |

## 7단계 — 내리기 → 되돌리기 → 대조 → 재적용 (기준 5)

| 순서 | 보낼 요청 | 기대 응답 | 기대하는 실제 행 변화 |
|---|---|---|---|
| 7-1 (선택) | 시험 전용 객체가 **남아 있는 채로** 되돌리기 SQL 실행 | 실패(`zz_b2a_*` 표의 정책이 판정 함수에 기대고 있음 — `2BP01`). 한 트랜잭션이라 아무것도 지워지지 않아야 한다 | 0 (`public.site_status`도 그대로 있어야 한다) |
| 7-2 | SQL: `fixtures_down.sql` 전체 | 오류 없음 | `public.zz_b2a_*` 표 4개·함수 4개·정책 사라짐 |
| 7-3 | SQL: 2-1의 질의로 `pgrst.db_pre_request` 항목이 없는지 다시 확인한 뒤, 되돌리기 SQL 전체 | 오류 없음(설정이 남아 있으면 첫 블록에서 `b2a 되돌리기 중단`으로 멈춘다) | `security_private` 스키마와 그 안의 표 5개·함수 7개, `public.site_status`·`public.my_site_access` 사라짐(표 안의 합성 대응·장부 행도 함께) |
| 7-4 | SQL: 아래 "남은 것 확인" | 세 질의 모두 0행 | — |
| 7-5 | SQL: 합성 회원(`public.users`의 A·B·E)을 지우고, 로그인 서버에서 합성 계정 A·B·N·G·E를 지운다 | 오류 없음 | `public.users` −3, `auth.users` −5, 관련 로그인 상태·인증 앱 등록 0 |
| 7-6 | SQL: 2-2의 지문 질의 전부, 2-1의 질의, 기준 요청 R1~R3 | 2단계에서 저장한 것과 전부 같음 | 없음 |
| 7-7 | SQL: 마이그레이션 파일 전체를 **다시** 실행(재적용) | 오류 없이 끝남(자기 점검 통과) | 3-1과 같은 객체가 다시 생김, `site_state` 1행 |
| 7-8 | `notify pgrst, 'reload schema';` 뒤 K0: `rpc/site_status` | `200`, `phase` `normal`, `maintenance_id` 0 | 없음 |

남은 것 확인:
```sql
select n.nspname from pg_catalog.pg_namespace n where n.nspname = 'security_private';

select n.nspname, p.proname
  from pg_catalog.pg_proc p join pg_catalog.pg_namespace n on n.oid = p.pronamespace
 where (n.nspname = 'public' and p.proname in ('site_status', 'my_site_access'))
    or p.proname like 'zz\_b2a\_%';

select n.nspname, c.relname
  from pg_catalog.pg_class c join pg_catalog.pg_namespace n on n.oid = c.relnamespace
 where c.relname like 'zz\_b2a\_%';
```
- 7-5의 순서 주의: 대응표가 살아 있는 동안에는 `public.users`의 합성 회원을 지울 수 없다(외래키). 되돌리기 SQL(7-3) 뒤에 지우거나, 그 전에 지우려면 `member_identity`·`access_grant`의 해당 행을 먼저 지운다.
- 7-6의 (사)(계정·로그인 상태 수)는 7-5까지 끝낸 뒤에 2단계와 같아야 한다.
- **7-7 뒤의 최종 상태**(재적용한 채로 둘지, 되돌리기 SQL을 한 번 더 실행해 비울지)는 계약서에 정해져 있지 않다. 브레인방이 정한다. 재적용한 채로 두는 경우 2-2의 지문은 그대로여야 하고(새 객체는 지문에서 빠져 있다), 공통 확인 설정은 원복된 상태여야 한다.
- "훅 재적용"(6-2)과 "마이그레이션 재적용"(7-7)은 서로 다른 확인이다. 둘 다 한다.

## 이 절차가 확인하지 않는 것

- 실제 화면·실제 업무(대리·책의 발급과 중계, 가입·비밀번호)는 이 계약 범위 밖이다. `resolve_grant`의 1행은 장부 확인일 뿐 실제 자료 접근 승인이 아니다.
- 파일(Storage) 규칙과 Edge 함수에서의 같은 판정은 이 절차에 없다(공통 확인은 PostgREST에만 걸린다).
- DB 안에서 도는 예약·트리거·직접 SQL은 공통 확인을 거치지 않는다.
- 동시에 많은 요청이 올 때의 응답 시간은 재지 않는다. 판정 함수는 jsonb 변환에 예외 처리 블록을 쓰므로 호출마다 작은 비용이 있다 — 정책에서는 `(select security_private.current_member_id())`처럼 감싸 한 번만 계산되게 쓰는 것을 권한다(`zz_b2a_member_row`가 그 형태, `zz_b2a_admin_flag`는 직접 부르는 형태다).
- 자격의 유효 시간(60분) 내내 같은 결과인지는 재지 않는다.
