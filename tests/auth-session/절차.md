# 계약 3A 화면 시험 절차 (브레인방용 — 시험 프로젝트 `hmncdheiwqwekdbtijar`, 실행기 `screen.mjs`)

작업방은 이 절차를 **가짜 서버를 상대로만** 돌렸다(`--fake`). 시험 프로젝트를 상대로 한 실행(`--real`)은 브레인방만 한다. 아래의 "기대"는 코드와 가짜 서버에서 나온 것이고 **실제 서버에서 확인된 것이 아니다.** 어긋나면 그 자체가 결과다 — 맞추려고 다시 돌리지 말고 그대로 적는다.

운영(`qpqjevecjejvbeuogtbx`)은 건드리지 않는다.

## 0. 준비

1. 브랜치 `보안작업-묶음2-공홈인증`의 head 를 새 폴더에 받는다. `node tests/auth-session/run.mjs` → 마지막 줄 `결과: 통과`(전부 가짜 — 실제 요청 0).
2. 시험 프로젝트에 적용돼 있어야 하는 것: 2-가(`my_site_access`), 3-0(`my_profile`). 점검은 꺼짐.
3. 합성 계정 일곱(이메일·비밀번호로 로그인할 수 있어야 한다. **비밀번호는 전부 같은 값**):

   | 이름 | 뜻 | `my_profile` 기대 |
   |---|---|---|
   | A, B | 정상 회원(A 는 점검 예외 명단에 넣을 계정) | `ok` |
   | BLK | 차단 | `blocked` |
   | WD | 탈퇴 처리 중 | `withdrawal_pending` |
   | N | 회원 대응이 없는 계정 | `no_member` |
   | G | 회원 대응 없는 관리자 | `no_member` |
   | GM | 회원 대응 있는 관리자 | `ok` |

4. 환경 변수(하나라도 틀리면 실행기가 아무 화면도 열지 않고 종료 코드 2):

   | 이름 | 값 |
   |---|---|
   | `B3A_PLAYWRIGHT` | `playwright-core` 폴더의 경로(실행기는 설치·내려받기를 하지 않는다) |
   | `B3A_CHROMIUM` | `chrome.exe` 의 경로 |
   | `B3A_TEST_URL` | 정확히 `https://hmncdheiwqwekdbtijar.supabase.co` |
   | `B3A_TEST_ANON_KEY` | 시험 프로젝트의 anon 키(다른 프로젝트의 키·service_role 키면 거절) |

   | `B3A_EMAIL_A`·`_B`·`_BLK`·`_WD`·`_N`·`_G`·`_GM` | 합성 계정의 이메일 |

   실행기는 이 값들과 JWT·갱신값을 출력·파일에 쓰지 않는다.

## 1. 실행

```
node tests/auth-session/screen.mjs --real --out <결과.json>
```

- 실행기가 **스스로** 로컬 서버 둘(켜짐·꺼짐 — `serve-core.mjs`)과 제어 포트를 `127.0.0.1` 에 띄운다. `serve.mjs` 는 손으로 화면을 볼 때만 쓴다(이 절차에는 필요 없다).
- 경우마다 **디스크에 남지 않는 새 브라우저 상태**에서 시작한다. 추적·HAR·상태 내보내기·화면 캡처는 하지 않는다.
- **모든 요청은 차단기(`request-log.mjs`)의 결정을 거친 뒤에만 나간다.**
  - 브라우저는 `127.0.0.1` 말고는 이름을 풀지 못하게 띄운다. 시험 프로젝트로 가는 요청은 차단기를 지난 뒤 **실행기가 대신 내보내고** 응답을 브라우저에 돌려준다.
  - 차단기는 목적지뿐 아니라 **자격의 종류와 용도**를 본다: 비밀번호는 로그인 요청에만, 갱신값은 갱신 요청에만, 회원 JWT 는 로그아웃(`scope=local`)과 두 RPC 에만. 맞지 않으면 시험 프로젝트로 가는 것이라도 전송 전에 중단한다. service_role·알 수 없는 자격은 어디로도 보내지 않는다.
  - 리디렉션 응답은 브라우저에 넘기지 않고 다음 주소를 차단기로 다시 가른다. 서비스 워커는 끈다. 허용 목록의 정적 자원(글꼴·모양·그림)은 **보내지 않고** 빈 응답을 돌려준다.
  - 실행기 자신이 여는 연결도 `127.0.0.1` 과 시험 프로젝트만 허용하고 센다.
- 맨 앞의 경우 **P(차단의 예행)** 가 차단이 실제로 듣는지를 먼저 입증한다. **같은 수신기(로컬 시험 목적지)** 로 본다: 먼저 차단하지 않은 정상 요청 1건을 그 수신기가 실제로 받는 것을 확인하고(이 한 건만 실행기가 일부러 보낸다 — **자격 위반 판정이 먼저**이고, 예외로 나갈 수 있는 것은 그 주소로 가는 자격 없는·본문 없는 GET 한 번뿐이다. 그 조건을 벗어난 요청이 그 주소로 오면 중단하고 P 는 통과가 아니다), 그 뒤 첫 화면·새 창·리디렉션·폼 제출·최상위 이동·제어 포트로 가는 요청을 시켜 보는 동안 **그 수신기의 추가 수신이 0** 인지 본다. **차단기가 센 시도 수**와 **목적지가 실제로 받은 수**는 따로 적는다. 화면 안의 fetch 가운데 바깥 주소·제어 포트로 가는 것은 내용 보안 정책이 차단기보다 먼저 막는다 — 그 수도 따로 센다.
- **P 의 판정이 전부 참일 때만 뒤의 경우를 시작한다.** 하나라도 거짓·미확인이면 그 자리에서 끝낸다(뒤의 경우는 "돌리지 않음", 전체 판정은 통과 아님, 종료 코드 4). 비밀번호·이메일은 보관함에 들어 있고 P 가 통과하기 전에는 꺼낼 수 없다 — 그 전에는 로그인도, 받은 로그인 상태를 브라우저에 넣는 일도 일어나지 않는다. `--only` 를 줘도 P 는 언제나 먼저 돈다.

## 2. 멈춤 — 브레인방이 사이에 끼는 단계

실행기가 멈추면 화면에 `[멈춤] 이름` 이 찍힌다. 제어 포트(`127.0.0.1:<포트>`)는 **머리글 `x-b3a-secret: <B3A_CONTROL_SECRET>`** 과 **그 멈춤의 일회용 단계 번호**가 둘 다 맞는 명령만 받는다(`127.0.0.1` 이라는 것은 권한 확인이 아니다. 시험 화면은 제어 포트에 닿지 못한다 — P 에서 입증).

```
GET  /wait                      → { "waiting": { "step": 123456, "kind": "…", "info": { … }, "needsRevert": false } }   (기다리는 것이 없으면 null)
POST /continue?step=123456      → 이어 간다. 본문이 필요한 멈춤은 JSON 본문과 함께
```

| 멈춤(`kind`) | 경우 | `info` | 브레인방이 할 일 | 보낼 본문 |
|---|---|---|---|---|
| `other-session-create` | 10 | `account: "A"` | A 의 로그인 기록을 하나 더 만든다(다른 기기 구실) | 없음 |
| `check-logout-scope` | 10 | `ended: <로그인 기록 번호>` | DB: 그 기록만 끝났고 위에서 만든 기록은 그대로인가 | `{"result":"ok"}` 또는 `{"result":"differs"}` |
| `check-records-intact` | T | `sids: [B 의 기록]`, `ended: A 의 기록` | DB: B 의 기록이 살아 있는가(끝나지도 갱신값이 바뀌지도 않음) | `{"result":"ok"}` / `{"result":"differs"}` |
| `expire-session` ⚠ | 14 | `sid` | 그 로그인 기록을 서버에서 끝낸다(3-0 시험의 `session_expire.sql` 방식) | 없음 |
| `restore-session` | 14 | `sid` | 되돌리고(`session_restore.sql`) **DB 에서 되돌려졌는지 직접 대조한다** | `{"reverted":true}` |
| `maintenance-on` ⚠ | 15 | `exception: "A"` | 점검을 켠다(예외 명단에 A — 3-0 시험의 `maint_on.sql`) | 없음 |
| `maintenance-off` | 15 | | 점검을 끄고(`maint_off.sql`) **DB 에서 꺼졌는지 직접 대조한다** | `{"reverted":true}` |
| `provide-session` | 17·18·19a·19b | `account`, `aal` | **그 합성 계정**의 살아 있는 로그인 기록(요구한 aal)을 만들어 로그인 상태를 준다 | `{"session":{…}}` — 키는 `access_token`·`token_type`·`expires_in`·`expires_at`·`refresh_token`·`user` 뿐(`user` 에 `id`·`email`). 이 값은 이 길로만 받고 디스크에 쓰지 않는다 |
| `revert-confirm` | (원복 대상이 남았을 때) | `of: <멈춤 이름>` | 아래 "원복 확인" | `{"reverted":true}` |

- 로그인 기록 번호는 비밀이 아니다. 결과 파일에는 적지 않는다(제어 포트의 `info` 로만 준다).
- 기다림의 상한은 10분(`--pause-timeout-ms`)이다. 넘으면 그 경우는 "미확인"으로 끝난다.
- **⚠ 표시가 있는 멈춤은 브레인방이 건 DB 변경이 남는다. 실행기는 그 멈춤을 내놓는 순간 "원복 대상"으로 표시한다**("계속"을 받았는지와 무관하다 — DB 를 바꾼 뒤 제어 응답이 유실돼도 표시는 남는다). 표시는 되돌리는 멈춤(`restore-session`·`maintenance-off`) 또는 `revert-confirm` 에 **`{"reverted":true}`** 를 받아야 지워진다. 본문 없는 "계속"으로는 지워지지 않는다.
- 표시가 남아 있으면 실행기는 **다음 경우를 시작하지 않고** `revert-confirm` 을 내놓는다(세 번까지). 그것도 상한을 넘기면 전체를 멈춘다(종료 코드 3, 전체 판정은 통과가 아님, 결과의 `pendingRevert` 에 남은 멈춤 이름). 그때는 시험 프로젝트의 점검·로그인 기록을 손으로 확인해 되돌린다. `GET /wait` 의 답에도 `pendingRevert` 가 있다.
- **받은 로그인 상태는 넣기 전에 출처를 확인한다**: JWT 의 발급자가 `https://hmncdheiwqwekdbtijar.supabase.co/auth/v1`, 역할 `authenticated`, 이메일(JWT 의 `email` 과 `user.email` 둘 다)이 그 멈춤이 요구한 합성 계정의 것(환경 변수의 값), `aal` 이 요구한 값, 로그인 기록 번호(`session_id`)가 있음, 만료까지 5분 이상, 정해 둔 키만. 하나라도 어긋나면 넣지도 보내지도 않고 그 경우는 "미확인"이다(결과의 `notes.sessionRefused` 에 이유가 정해 둔 이름으로).
- `other-session-create`·`provide-session` 은 원복 대상은 아니지만 **브레인방이 만든 로그인 기록이 남는다** — 결과의 `operatorLeftovers` 에 적힌다. 정리는 끝에서 브레인방이 DB 로 한다.

두 확인 요청(`my_profile`·`my_site_access`)의 횟수: 로그인부터 `index.html` 의 표시까지 **`login.html` 에서 각 1회 + 새로 열린 `index.html` 에서 각 1회**(저장된 로그인을 다시 확인하므로).

## 4. 결과 읽는 법

결과 JSON(`--out`)에는 **정해 둔 판정값·이름·수만** 있다(화면·응답에서 읽은 글자, 주소, 키 이름, 로그인 기록 번호는 없다).

| 항목 | 뜻 |
|---|---|
| `overall` | `pass` 는 필수 경우가 전부 통과이고 돌리지 않은 경우가 없고 아래 독립된 증거가 깨끗할 때만. 실행하지 못한 필수 경우가 하나라도 있으면 `not-pass` |
| `totals` / `notRun` / `stopped` | 통과·기대와 다름·미확인의 수, 돌리지 않은 경우, 멈춘 이유 |
| `cases[].checks` | 판정 이름과 참/거짓/null(재지 못함) |
| `cases[].records` | 요청마다: 무리(`where`)·이름(`target`)·자격의 종류·비밀번호/갱신값이 실렸는가·중단했는가·실제로 보냈는가(`sent`)·어떻게(`how`)·응답의 상태와 오류 코드(정해 둔 이름) |
| `cases[].storage` | 저장소의 키 무리별 읽기·쓰기·지우기 횟수(값은 없다) |
| `summary.leakSent`·`outsideSent` | **차단기의 결정을 센 것**이다(차단기가 보내 준 위반 0) |
| `independentEvidence.sinkReceived`·`sinkControlPass`·`sinkUnexpected` | 로컬 시험 목적지가 **실제로 받은 수** — 차단기와 독립된 증거. 예행이 일부러 보낸 대조용 1건(`sinkControlPass` = 1) 말고는 0 이어야 한다(`sinkUnexpected` = 0) |
| `vaultOpened`·`started` | 예행이 통과해 비밀 보관함이 열렸는가, 시작한 경우들 |
| `pendingRevert`·`operatorLeftovers`·`pauses` | 원복 확인을 받지 못한 멈춤(null 이어야 한다), 브레인방이 만든 것이 남을 수 있는 멈춤들, 멈춤마다의 결과(answered / timeout) |
| `independentEvidence.runnerConnections` | 실행기가 연 연결: 로컬 / 시험 프로젝트 / 막은 시도(0 이어야 한다) |
| `independentEvidence.controlRejected` | 제어 포트가 거절한 요청(비밀·단계 번호가 맞지 않은 것) |

종료 코드: 0 통과 / 1 통과 아님 / 2 환경 변수·경로 / 3 원복 확인을 받지 못함·도중 중단 / 4 예행(P) 실패로 뒤의 경우를 돌리지 않음 / 5 결과에 비밀값의 흔적(파일을 쓰지 않음).

덧붙이는 점검으로 실행기는 결과에 비밀번호·이메일·공개 키·JWT 모양이 있으면 파일을 쓰지 않는다. 이 찾기는 갱신값 같은 것을 다 잡지 못한다 — 주된 보호는 "정해 둔 값만 적는다"이다.

## 4-1. 실행기 자신의 대조 실험 (`--fake` 에서만)

일부러 고장을 내고 실행기가 멈추는지 본다. 시험 프로젝트를 상대로는 쓸 수 없다(`--real` 과 함께 주면 종료 코드 2).

| 명령 | 고장 | 기대 |
|---|---|---|
| `--fake --selftest leaky-blocker` | 차단기가 시험 목적지로 가는 요청을 보내 준다 | P 가 기대와 다름, 뒤의 경우 0개 시작, 보관함 닫힘, 종료 코드 4 |
| `--fake --selftest bad-control-pass` | 예행의 대조용 요청을 자격·본문이 실린 POST 로 보낸다 | 예외로 나가지 않음(시험 목적지 수신 0), P 가 기대와 다름, 뒤의 경우 0개 시작, 종료 코드 4 |
| `--fake --selftest silent-operator --only 14,15 --pause-timeout-ms 4000` | 조작자가 로그인 기록 만료와 원복 확인에 답하지 않는다 | 14 미확인, 15 를 시작하지 않음, `pendingRevert` = `expire-session`, 종료 코드 3 |
| `--fake --selftest bad-session --only 17,18,19a,19b` | 조작자가 다른 계정·다른 aal·다른 발급자의 로그인 상태를 준다 | 넷 다 미확인(`notes.sessionRefused`), 그 로그인 상태로 나간 요청 0 |

## 5. 이 실행기로 확인되지 않는 것

- **교차 출처 허용**: 요청을 실행기가 대신 내보내고, 사전 요청(preflight)은 자동화 도구가 대신 답한다. 실제 브라우저가 `127.0.0.1`(나중에는 공홈 주소)에서 시험 프로젝트로 직접 보낼 때 허용되는지는 이 실행기로 확인되지 않는다.
- 응답의 내용은 실제 서버의 것이지만(`--real`), 연결은 브라우저가 아니라 실행기가 맺는다.
- 9b 는 브라우저가 화면을 되살릴 때만 잰다. 12 의 갱신은 브라우저의 시계를 앞으로 돌려 일으킨 것이다(수명 설정을 바꾸지 않는다).
- 허용 목록의 정적 자원을 보내지 않으므로 글꼴·아이콘 없이 그려진다(표시 판정에는 쓰지 않는다).
- DB 쪽 사실(다른 기기의 로그인 기록 불변 등)은 브레인방이 멈춤에서 확인해 준 값이다.

## 6. 끝

- 실행기가 끝나면 서버·브라우저가 닫힌다. `tests/auth-session/.run/` 의 결과는 커밋하지 않는다(무시 목록).
- 시험 프로젝트: 만든 로그인 기록·점검 상태·합성 계정을 3-0 때와 같은 방식으로 정리(만든 것만). R2 는 A 의 로그인 기록 하나의 갱신값을 소모한다.
- 적을 것: 경우별 결과(통과·기대와 다름·미확인을 따로), 14 번의 `notes.refreshRefusalCode`, 기대와 달랐던 것.

## 작업방이 확인하지 못한 것 (실제 서버에서 처음 보게 되는 것)

- 실제 로그인 서버의 응답 모양: 틀린 비밀번호의 오류 코드(`invalid_credentials` 가 아니면 문구가 "로그인 중 오류…"로 나온다), 끝난 로그인 기록의 갱신·로그아웃에 주는 코드(모듈이 "끝남"으로 보는 것은 `session_not_found`·`session_expired` 뿐이다 — 그 밖은 "모름"으로 처리돼 로그인이 브라우저에 남는다).
- 3-0 시험의 `session_expire.sql` 로 끝낸 기록의 갱신을 로그인 서버가 거절하는지, 거절한다면 어떤 코드인지.
- 합성 계정들이 이메일·비밀번호로 로그인되는지(작업방은 계정을 보지 못했다).

# 계약 3C-1 — 대상 화면 26개의 로그인 상태 통일 (같은 실행기 `screen.mjs` 가 이어서 돈다: 경우 C1~C17·CO)

위의 3A 절차(준비·실행·멈춤·결과)는 그대로다. 아래는 3C-1 에서 **더해지는 것**만 적는다.
이 조각은 **요청의 자격을 바꾸지 않는다** — 업무 요청은 전부 지금처럼 공개 키로 나가게 돼 있다. 실행기의 통과는 "화면이 서버에 확인된 로그인 상태만 쓴다"의 증거이지, 업무 요청의 성공·서버의 보호의 증거가 아니다.

## 3C-1 의 0. 준비 (3A 의 준비에 더해)

- **더 준비할 것이 없다.** 합성 업무 자료(SQL)도, 더 줄 환경 변수도 없다(1차에 있던 `B3C_APP_A`·`B3C_MEMBER_IDS`·`b3c1_fixtures_*.sql` 은 없앴다). 실행기는 업무 표를 읽지도 쓰지도 않는다.
- **시간 나누기**: 이 실행은 시험 프로젝트의 로그인 기록을 만들고, C5 는 로그인 기록 하나를 끝냈다 되돌리며, C17 은 점검을 켰다 끈다(3A 의 14·15 와 같은 멈춤). 3B·3C-DB 의 시험과 같은 시간에 돌리지 않는다.

## 3C-1 의 1. 업무 요청은 하나도 내보내지 않는다

- **시험 프로젝트로 실제 나가는 것은 3A 에서 승인된 인증 요청 다섯뿐이다**(로그인·갱신·로그아웃 `scope=local`·`rpc/my_profile`·`rpc/my_site_access`). `--real` 에서도 같다. 끄는 인자가 없다.
- 그 밖에 시험 프로젝트로 가는 요청(업무 요청 — 표·RPC·파일·함수)은 **전부 전송 전에 막고**, 실행기가 **가짜 응답**을 준다. 가짜 응답의 자료는 이번 실행의 합성 계정 값(이메일, `my_profile` 의 응답에서 본 회원번호·이름)으로 만든다 — `--fake` 와 `--real` 이 같은 모양이다. 가짜 응답에만 있는 신청서 번호 하나(A 의 것)와 글 번호 하나를 쓴다(시험 프로젝트의 DB 에는 없다).
- **가짜 응답으로 그려진 화면은 실제 업무 성공이 아니다.** 판정은 **시도**로 한다: 차단 전의 시도를 전부 기록하고(갈래 `write`·`partial-search`·`unconditioned`·`read`·`other` 와, 조건의 값이 어느 합성 계정의 것인지의 이름표), 닫힌 갈래·확인 전·확인되지 않음에서의 업무 요청은 **가짜 응답을 받았더라도 시도한 것 자체가 실패**다.
- 막는 자리가 둘이다. (1) 차단기(`request-log.mjs`)가 업무 요청을 "보내지 않음"으로 가른다. (2) **전송 지점**이 차단기의 결정과 따로 주소를 다시 보고, 다섯이 아니면 내보내지 않는다. 결과의 독립 증거:
  - `independentEvidence.businessSentToTestProject` — 0 이어야 한다.
  - `independentEvidence.wireSentByName`·`wireSentTotal` — 전송 지점을 지난 요청의 수(다섯 이름으로만 센다). `requestsSentToTestProject`(`--real`) 또는 `requestsAnsweredByFakeServer`(`--fake`)와 같아야 한다.
  - `independentEvidence.businessRefusedAtSendPoint` — 차단기를 지나 전송 지점까지 온 업무 요청. 0 이어야 한다(왔어도 내보내지 않지만, 0 이 아니면 전체 판정은 통과가 아니다).
  - `independentEvidence.runnerConnections` — 실행기가 연 연결(로컬 / 시험 프로젝트 / 막은 시도).
  - `summary.businessAttempts` — 시도의 수(갈래마다). **업무 성공의 수가 아니다.**
- 글 한 편을 여는 화면(공지·후기·학습 자료)은 지금처럼 조회수를 올리는 쓰기(PATCH)를 **시도**한다 — 지금의 동작이고, 전송 전에 막는다(`businessAttempts.write` 에 세어진다).
- 3A 의 경우들(1~O5)도 같은 규칙으로 돈다.

## 3C-1 의 4. 실행기 자신의 대조 실험 (`--fake` 에서만 — 3A 의 넷에 하나 더)

```
node tests/auth-session/screen.mjs --fake --selftest leaky-business --only C2,C9,C10
```

차단기가 고장 나 업무 요청을 "보냄"으로 가르게 한다. 기대: **전송 지점이 따로 막는다** — 가짜 서버가 받은 업무 요청 0(`businessArrivedAtFakeServer`), 전송 지점까지 온 업무 요청이 0 이 아니게 세어지고(`businessRefusedAtSendPoint`), 그 경우들의 판정은 "기대와 다름", 전체 판정은 통과 아님(종료 코드 1).

## 3C-1 의 5. 끝

1. 실행기의 끝 지문: `전체 판정: 통과`, `시험 목적지 수신 1(대조용 1 + 그 밖 0)`, `막은 시도 0`, `pendingRevert: null`, `업무 요청: 실제로 나간 것 0건`, `전송 지점까지 온 업무 요청 0건`.
2. 지울 합성 업무 자료가 없다(넣지 않는다). 실행기가 만든 로그인 기록(합성 계정의 것)은 3A 와 같이 브레인방이 DB 로 정리한다(`operatorLeftovers`).
3. C5·C17 의 원복(`{"reverted":true}`)을 직접 대조한 뒤에 답한다.

## 3C-1 에서 이 실행기로 확인되지 않는 것

- **업무 요청의 실제 성공과 실제 응답의 모양으로 화면이 그려지는가** — 업무 요청은 하나도 내보내지 않는다. 가짜 응답의 모양(열 이름·값)은 작업방이 화면의 코드를 읽고 지은 것이다. 실제 응답으로 그려지는가는 3C-2 의 일이다.
- **서버의 보호** — 이 조각은 자격을 바꾸지 않는다.
- **A 의 초안**: 사람이 달라지면 그 탭은 다시 받고, 다시 받기 전에 칸을 처음 값으로 돌린다 — A 가 그 탭에 적던 값은 사라진다(C7 의 `notes`). 화면이 따로 저장해 둔 임시 저장(신청서 화면의 것 등)이 계정마다 나뉘는지는 이 실행기가 보지 않는다.
- 다른 탭에서 **같은 사람**이 로그아웃했다 다시 로그인하면, 그 사이의 "로그인 전"에서 회원 화면은 다시 받는다(적던 값이 사라진다) — C14 는 한 탭 안의 재확인만 본다.
- **뒤로 가기로 되살아난 화면**은 브라우저가 되살릴 때만 잴 수 있다(C3b). 가짜 서버 상대로는 빈 화면으로 떠났을 때 되살아났고, 인증 모듈을 싣는 다른 화면으로 떠났을 때는 되살아나지 않았다.
- 위 표의 미실행 조합.
