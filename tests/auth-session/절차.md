# 계약 3A 화면 시험 절차 (브레인방용 — 시험 프로젝트 `hmncdheiwqwekdbtijar`, 실제 브라우저)

작업방은 이 절차의 어느 단계도 실행하지 않았다(Supabase 로 요청 0). 아래의 "기대"는 코드와 가짜 서버 시험에서 나온 것이고, **실제 서버에서 확인된 것이 아니다.** 어긋나면 그 자체가 결과다 — 맞추려고 다시 돌리지 말고 그대로 적는다.

운영(`qpqjevecjejvbeuogtbx`)은 건드리지 않는다. 시험 서버는 운영 흔적이 남은 파일을 내주지 않고, 브라우저의 연결은 자기 자신과 시험 프로젝트 출처로만 나간다.

## 1. 브라우저 자동화의 설정 (먼저 — 첫 화면을 열기 전에)

- **경우마다 새 브라우저 프로필**(저장소가 빈 상태)에서 시작한다.
- **모든 요청을 전송 전에 가른다.** `tests/auth-session/request-log.mjs` 의 `makeDecider({ selfOrigin: 'http://127.0.0.1:8787', anonKey })` 가 요청 하나를 받아 `continue`/`abort` 와 가린 기록 한 줄을 돌려준다(파일 머리의 예). 자동화가 `abort` 를 **전송 전에** 실행해야 한다.
  - 계속: 자기 자신(`127.0.0.1:8787`), 시험 프로젝트 출처로 가는 fetch, 허용 목록의 정적 자원(글꼴·모양: `cdn.jsdelivr.net`·`fonts.googleapis.com`·`fonts.gstatic.com`, 그림: `eontoefl.github.io` — GET 만).
  - 중단: 그 밖의 모든 것. **최상위 화면 이동·폼 제출도**(내용 보안 정책은 화면 이동을 막지 못한다 — 여기서 막는다). 시험 프로젝트 출처로 가는 화면 이동과 로컬 시험 목적지(`/__b3a/sink/…`)로 가는 요청도 중단하고 센다.
- 기록 규칙: 비밀번호·JWT·갱신값을 남기지 않는다. `request-log.mjs` 의 기록은 자격의 종류(`none`/`anon`/`member`)와 본문의 키 이름만 남긴다. 저장소를 볼 때 `eon_auth_v1` 의 **값은 읽어 적지 않는다**(키 이름과 "있음/없음"만). 화면 캡처에 비밀번호 입력란의 값이 보이지 않게 한다.
- 상태는 화면의 콘솔에서 읽는다: `EonAuth.state()`, `EonAuth.reason()`, `EonAuth.profile()`(여섯 열), `EonAuth.siteAccess()`.

## 3. 켜짐 — 기존 로그인 상태와의 격리

새 프로필에 아래 값을 **자동화가 저장소에 직접 넣고** 시작한다(그 화면들을 열 필요 없다). 값은 지어낸 것으로 충분하다.

| 상태 | 넣는 것 |
|---|---|
| 옛 학생 | `iontoefl_user`(옛 모양: `id,name,nickname,email,phone,level,role`), `iontoefl_login_time` |
| 교재 편집만 | `eon_book_auth_v1` |
| 후속메일만 | `sb-hmncdheiwqwekdbtijar-auth-token` |
| 섞임 + 만료 | 위 셋 + 만료 시각이 지난 값 |

- 옛 학생·섞임: `login.html?redirect=my-dashboard.html` 을 열어도 **자동 이동 0**. A 로 로그인하면 "기존 방식의 로그인 상태가 있습니다. 기존 방식에서 로그아웃한 뒤 다시 로그인해 주세요." — 인증 요청 0, `iontoefl_user` 가 글자 그대로. `index.html` 은 옛 값으로 이름을 그리지 않는다(`LOGIN | JOIN`).
- 교재 편집만·후속메일만: A 로그인 → `index.html` → 로그아웃까지 한 뒤, 넣어 둔 값이 **글자 그대로**인지 본다.
- 어느 상태든 기존 업무 요청(예: `index.html` 의 후기 목록, 로그인한 회원의 신청서 조회)의 자격은 `anon` 이다(기록의 `credential`).

## 4. 꺼짐 대조 (서버 `--mode off`, 같은 다섯 상태)

- 인증 모듈의 흔적 0: `/auth/v1/`·`/rpc/my_` 로 가는 요청 0, `vendor/supabase-2.116.0.js` 를 받는 요청 0, 저장소에 `eon_auth_v1…` 키 0, `EonAuth.state()` = `off`.
- 옛 동작 그대로: 옛 학생 상태에서 `login.html?redirect=…` 은 지금처럼 그 주소로 자동 이동, 머리말에 옛 이름, LOGOUT 은 저장소의 두 값만 지우고 새로 고침(요청 0).
- 주소에 `?eon_auth=on` 같은 꼬리표를 붙이거나 저장소·쿠키에 값을 넣어도 켜지지 않는다.
- 꺼짐의 옛 로그인(`login.html` 제출)은 **회원 표 전체를 읽는다**(지금 코드가 그렇다 — 시험 프로젝트의 회원 표에서). 대조에 꼭 필요하지 않으면 제출까지는 하지 않는다.

## 6. 끝

- 서버 둘을 멈춘다. `tests/auth-session/.run/` 의 기록은 커밋하지 않는다(무시 목록).
- 시험 프로젝트: 만든 로그인 기록·점검 상태·합성 계정을 3-0 때와 같은 방식으로 정리(만든 것만).
- 적을 것: 경우별 결과(허용·거절·화면 결과·미확인을 따로), 기대와 달랐던 것, 확인하지 못한 것.

## 작업방이 확인하지 못한 것 (실제 서버에서 처음 보게 되는 것)

- 실제 로그인 서버의 응답 모양(틀린 비밀번호의 오류 코드가 `invalid_credentials` 로 오는지 — 아니면 문구가 "로그인 중 오류…"로 나온다), 갱신 거절의 모양, 로그아웃 응답.
- `503`(점검) 응답을 브라우저가 읽을 수 있는지(교차 출처 머리글이 없으면 fetch 가 실패로 끝나 "로그인 중 오류…"가 된다).
- 실제 브라우저에서의 SDK 동작(탭 사이 알림, 탭 전환 때의 갱신, 뒤로 가기 보관). 가짜 화면에서는 SDK 사본을 그대로 올려 봤지만 실제 브라우저가 아니다.
- 로컬 주소(`http://127.0.0.1:8787`)에서 시험 프로젝트로 가는 교차 출처 요청이 허용되는지(머리글 `apikey`·`authorization`·`x-supabase-api-version`).
